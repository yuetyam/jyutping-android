Plan: Implement input memory export and import for Android, compatible with the iOS and macOS versions.

Status: Implemented (2026-11-08)

## Goal

Let users export the learned entries in `memory.sqlite3` to one portable SQLite file at a location they choose, and import such a file back, merging its entries into the live memory without losing existing ones.

The file format is the version-1 format already shipped by the macOS input method and the iOS keyboard (`~/swift/Jyutping/InputMethod/InputMemory/InputMemoryExporter.swift`, `Keyboard/SharedModels/InputMemoryExporter.swift`, and `InputMemoryImporter.swift` in both). A file exported on any platform must import on every other platform.

## Reference: iOS/macOS behaviour to match

- Export: snapshot the live store, stream `word`, `romanization`, `frequency`, `latest` from every `memory2608` row into a fresh database, build indexes, set `user_version = 1`, validate, then publish. Suggested filename `memory-yyyyMMdd-HHmmss.sqlite3` (Gregorian calendar, POSIX locale, local time zone). Empty memory produces a valid file with an empty table. Disabling learning does not disable export.
- Import: capture a private copy of the selected file, validate it, then merge valid rows in one transaction with `MAX(frequency)` and `MAX(latest)`, so re-importing the same file changes nothing. Invalid rows are skipped; unsupported files leave memory unchanged. The reported count is the number of valid rows merged.
- UI: Export and Import buttons next to Clear Input Memory. Export, import, and Clear exclude one another. Progress is shown while running; the result is reported with a row count or a categorized error. Picker cancellation reports nothing.

## File format (version 1, unchanged)

```sql
CREATE TABLE input_memory (word TEXT NOT NULL, romanization TEXT NOT NULL, frequency INTEGER NOT NULL, latest INTEGER NOT NULL, UNIQUE (word, romanization));
CREATE INDEX ix_input_memory_frequency ON input_memory (frequency);
CREATE INDEX ix_input_memory_latest ON input_memory (latest);
PRAGMA user_version = 1;
```

- Journal mode `DELETE`; the published file needs no `-wal`/`-shm` sidecars.
- `latest` is Unix time in milliseconds (Android already stores `System.currentTimeMillis()`).
- The table `CREATE` statement must be byte-identical to the iOS/macOS one, because their validators compare `sqlite_master.sql`.
- Readers accept extra columns, missing constraints, and missing explicit indexes; they require `user_version = 1`, the four columns, and a passing `PRAGMA integrity_check`.
- Row validation on import: `word` is nonempty TEXT; `romanization` is TEXT containing at least one lowercase basic Latin letter and otherwise only lowercase basic Latin letters, tone digits `1`–`6`, and spaces; `frequency` and `latest` are positive INTEGER values. Android's derived `anchors_9key` and `spell_9key` are rebuilt on import, as are the other derived fields.

## Current Android integration points

- `memory/InputMemoryHelper.kt`: `SQLiteOpenHelper` for `memory.sqlite3` (version 3, table `memory2608`, WAL). `prepare()` runs the legacy migration; readiness is a process-wide `@Volatile isMigrating` flag that callers poll and silently return on. `deleteAll()` and `forget()` are no-ops while migrating.
- `memory/MemoryLexicon.kt`: `MemoryLexicon.new(word, romanization, frequency, latest)` already rebuilds every derived field, including the nine-key ones; the importer reuses it.
- `JyutpingInputMethodService.kt`: owns a private `memoryHelper by lazy { InputMemoryHelper(applicationContext) }`, calls `prepare()` from `onCreate()` on `Dispatchers.IO`, learns on commit, and `clearInputMemory()` calls `deleteAll()`.
- `keyboard/SettingsScreen.kt` (around lines 1040–1130): the Input Memory section with the toggle and the Clear button plus confirmation.
- `MainActivity`, `AppContent.kt`, `Screen.kt`, `app/home/HomeScreen.kt`: launcher navigation.
- `AndroidManifest.xml`: no storage permissions, which are not needed when using the Storage Access Framework.
- The launcher activity and the IME service run in the same default process.

## Key design decisions

### 1. Where the transfer runs: the launcher app (decided 2026-11-08)

The keyboard settings are rendered inside an `InputMethodService` window. A service cannot register an `ActivityResultLauncher`, and SAF pickers need an Activity to return their result.

Export and import live in a launcher-app screen, `Screen.InputMemory`, with Export, Import, and result feedback. In `keyboard/SettingsScreen.kt`, Export and Import rows start `MainActivity` with an extra that navigates to this screen (`FLAG_ACTIVITY_NEW_TASK`), and dismiss the keyboard. This gives one implementation, a normal lifecycle for pickers and progress, and an operation that survives the keyboard being hidden.

A translucent trampoline Activity launched from the IME was considered and rejected: feedback, progress, and cancellation are awkward in a window-less Activity.

### 2. Picker contracts

- Export: `ActivityResultContracts.CreateDocument("application/vnd.sqlite3")` with the suggested filename. Unlike the iOS keyboard (which picks a folder because its save panel cannot lay out in the keyboard window), Android's create-document UI lets the user choose name and location, and the provider handles name collisions.
- Import: `ActivityResultContracts.OpenDocument()` with `arrayOf("application/vnd.sqlite3", "application/x-sqlite3", "application/octet-stream")`. Many providers report `.sqlite3` as `application/octet-stream` or an empty type; if testing shows files are greyed out, fall back to `*/*` and rely on validation.
- No persistable URI permission is needed; the grant lasts for the operation.

### 3. Consistent snapshot without the SQLite backup API

The Android framework does not expose `sqlite3_backup`. Use `VACUUM INTO '<private file>'` on a connection to the live store: it runs as one read transaction, so under WAL it captures a consistent snapshot without blocking the IME's learning writes, and produces a standalone file. Android 13 ships SQLite 3.32+, which supports `VACUUM INTO` (3.27+). Bind the path rather than interpolating it, or interpolate only an app-generated cache path with quotes escaped.

Fallback if `VACUUM INTO` proves unavailable on a device: stream rows inside one explicit transaction on the helper's connection. Do not rely on a plain `Cursor` for snapshot consistency, because `SQLiteCursor` re-executes the query when it refills its window.

### 4. One shared `InputMemoryHelper` and an explicit readiness API

Today the IME creates its own helper, and `prepare()` only runs when the IME is created. Export from the launcher could run before migration has ever started, and polling `isMigrating` cannot distinguish "ready" from "never prepared" or "failed".

- Make `InputMemoryHelper` a process-wide singleton (`InputMemoryHelper.shared(context)` in the companion) used by both the service and the launcher, so all access goes through one connection pool.
- Add `suspend fun ensureReady(): Result<Unit>` guarded by a `Mutex`: runs `prepare()` on `Dispatchers.IO` if not yet migrated, awaits a migration already in progress, and returns failures instead of swallowing them.
- Harden `migrateMemory()`: reset `isMigrating` in a `finally`, persist a frequency-band checkpoint only after its transaction commits (already the case), and leave state retryable on failure. Keep the existing migration keys, legacy-table selection, and frequency-band policy unchanged.

## Implementation sequence

### Step 1: Shared helper and readiness

- `memory/InputMemoryHelper.kt`: add the singleton accessor, `ensureReady()`, a `databasePath` accessor (`context.getDatabasePath(DATABASE_NAME)`), and the `try/finally` around migration.
- `JyutpingInputMethodService.kt`: replace the private `InputMemoryHelper(applicationContext)` with the shared instance; keep `prepare()` in `onCreate()` (or call `ensureReady()`).
- Add a process-wide transfer state: `isTransferring: StateFlow<Boolean>`. `handle()` (learning) may continue during export; `deleteAll()` must refuse while a transfer is active, and transfers must refuse while Clear is running.

### Step 2: `memory/InputMemoryExporter.kt`

Pure, testable function with no UI or `Uri` handling:

```kotlin
object InputMemoryExporter {
        /** Writes a validated version-1 export to [output], which must not exist. Returns the row count. */
        suspend fun export(helper: InputMemoryHelper, output: File): Long
}
```

1. `ensureReady()`.
2. Create a private workspace under `context.cacheDir`; `VACUUM INTO` a snapshot file there.
3. Open the snapshot read-only and a new output database (`SQLiteDatabase.openOrCreateDatabase`), set `PRAGMA journal_mode = DELETE`, then in one output transaction: create the table, set `user_version = 1`, stream the four columns through one compiled insert statement with `bindString`/`bindLong`, verify the count against `SELECT COUNT(*) FROM memory2608` on the snapshot, and create the two indexes.
4. Close both, reopen the output read-only, and validate `user_version`, row count, the `sqlite_master.sql` text, and `PRAGMA integrity_check`.
5. Call `currentCoroutineContext().ensureActive()` per row and between phases. On any failure or cancellation, delete the output and its sidecars. Always delete the workspace.

### Step 3: `memory/InputMemoryImporter.kt`

```kotlin
sealed class InputMemoryImportError : Exception() { data object UnsupportedFormat : InputMemoryImportError() }
object InputMemoryImporter {
        /** Merges valid rows from a private copy of an export. Returns the number of merged rows. */
        suspend fun import(helper: InputMemoryHelper, file: File): Long
}
```

1. The caller has already copied the picked `Uri` into a private file (Step 4); the importer never touches the provider again.
2. Open the private copy read-write (it is private, and this lets SQLite handle a WAL-mode header), set `journal_mode = DELETE`, then validate version, table, columns, and integrity. Any open or validation failure becomes `UnsupportedFormat`.
3. `ensureReady()`, then on the helper's writable database run one `beginTransaction()` / `setTransactionSuccessful()` / `endTransaction()` block, streaming rows through one compiled statement:

```sql
INSERT INTO memory2608 (word, romanization, frequency, latest, char_count, letter_count, complexity, anchors, spell, anchors_9key, spell_9key) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?) ON CONFLICT (word, romanization) DO UPDATE SET frequency = MAX(frequency, excluded.frequency), latest = MAX(latest, excluded.latest);
```

4. Read each column with `cursor.getType()` first, so non-TEXT and non-INTEGER values are skipped rather than coerced; build entries with `MemoryLexicon.new(...)`; apply the same romanization validation as iOS using the existing `isLowercaseBasicLatinLetter` and `isCantoneseToneDigit` extensions.
5. Cancellation or any error ends the transaction without success, rolling back every change. Delete the private copy.

Using the helper's own connection means the IME's learning writes wait in the framework's connection pool for the short transaction instead of failing with `SQLITE_BUSY`.

### Step 4: Transfer controller and `Uri` I/O

Add `memory/InputMemoryTransferController.kt` (an application-scoped singleton, or a `ViewModel` on the launcher screen if operations need not outlive it):

- State: `isExporting`, `isImporting`, and `feedback` as `StateFlow`s, so the launcher screen and the keyboard settings can both reflect them.
- Export: build into a private cache file with `InputMemoryExporter`, then copy it to the picked `Uri` via `contentResolver.openOutputStream(uri, "wt")`. If the copy fails, attempt `DocumentsContract.deleteDocument()` on the newly created document. Success is reported only after the stream is flushed and closed.
- Import: copy `contentResolver.openInputStream(uri)` into a private file (with a size sanity limit), then call `InputMemoryImporter`.
- Run SQLite and stream work on `Dispatchers.IO`. Map errors to feedback categories:
  - Export: success with count, memory busy or migrating, validation failed, write failed, export failed.
  - Import: success with count, unsupported file, memory busy, import failed (no entries changed).

### Step 5: UI

- `Screen.kt` / `AppContent.kt`: add `Screen.InputMemory`; add an entry to it in `HomeScreen.kt`. The screen has the Export and Import buttons with an indeterminate progress indicator, and shows feedback in an `AlertDialog` or `Snackbar`.
- `MainActivity`: handle an intent extra that navigates directly to `Screen.InputMemory`.
- `keyboard/SettingsScreen.kt`: under the Clear row in the Input Memory section, add Export and Import rows that open the launcher screen (and optionally start the picker immediately via a second extra). Disable Clear while `isTransferring` is true, and guard the confirmation action too.
- Suggested filename comes from `SimpleDateFormat("yyyyMMdd-HHmmss", Locale.US)` with the default time zone, or `DateTimeFormatter` with `IsoChronology` and `Locale.ROOT`.

### Step 6: Localization

Add keys to `values/strings.xml` and each `values-b+*` directory that overrides the existing `keyboard_settings_clear_input_memory*` keys (about 20 directories), for example:

- `input_memory_export_button`, `input_memory_import_button`, `input_memory_screen_title`
- `input_memory_export_progress`, `input_memory_export_success` (plural or `%1$d`), `input_memory_export_busy`, `input_memory_export_validation_failed`, `input_memory_export_write_failed`, `input_memory_export_failed`
- `input_memory_import_progress`, `input_memory_import_success`, `input_memory_import_unsupported`, `input_memory_import_busy`, `input_memory_import_failed`
- `input_memory_dismiss`

Reuse the iOS wording where it fits (`~/swift/Jyutping/Keyboard/Localizable.xcstrings`, keys `SettingsView.ExportInputMemory.*` and `SettingsView.ImportInputMemory.*`), keeping Cantonese (`yue`) and Chinese (`zh`) as separate families with their existing regional wording. Use `<plurals>` for the counts in English.

### Step 7: Validation

JVM unit tests are disabled for `:app`, and Android's `SQLiteDatabase` is not available on the JVM, so automated coverage goes in `app/src/androidTest/` and runs with `./gradlew :app:connectedDebugAndroidTest` on an emulator. Keep the exporter and importer `File`-based so these tests need no UI.

Automated coverage:

- Exact round trip: Unicode words (including supplementary-plane characters and an embedded `\u0000`), tone digits, double spaces, frequencies and timestamps beyond 32-bit range; reimport is idempotent; derived fields, including `anchors_9key` and `spell_9key`, match `MemoryLexicon.new`.
- Empty memory, `user_version`, schema text identical to iOS/macOS, integrity, no sidecars after close.
- Merge keeps the larger frequency and later timestamp, and keeps entries absent from the file.
- Invalid rows skipped; extra columns tolerated; missing table, missing column, wrong version, non-SQLite, and empty files rejected with memory unchanged.
- Export during concurrent `handle()` writes yields a consistent snapshot; import during concurrent learning does not fail or partially apply.
- Cancellation and forced failures roll back and clean temporary files.
- `ensureReady()` before the IME has ever started, during migration, and after an injected migration failure.

Cross-platform checks: import a file exported by the macOS input method and by the iOS keyboard, and verify that an Android export imports on both.

Manual checks on device/emulator with the installed IME: entry from the keyboard settings and from the launcher, Downloads and Google Drive providers for both pickers, picker cancellation, filename collision handling, learning disabled, Clear disabled while transferring, typing during export and import, and rotation or backgrounding mid-operation.

Build checks: `./gradlew :app:compileDebugKotlin`, `./gradlew :app:assembleRelease` (R8), and `git diff --check`.

## Out of scope / follow-ups

- Auto Backup: `allowBackup="true"` with template `backup_rules.xml` and `data_extraction_rules.xml` currently back up everything by default, including `memory.sqlite3`. Decide separately whether to define explicit rules.
- Emoji frequency is cleared together with input memory but is not part of the export format, same as iOS/macOS.
- A future format version 2 must keep version-1 import working on every platform.

## Completion criteria

- Export produces one portable version-1 `.sqlite3` file at the chosen location, byte-compatible in schema with iOS/macOS exports.
- Import accepts version-1 files from any platform, merges valid rows atomically with the larger frequency and later timestamp, skips invalid rows, and rejects unsupported files without changing memory.
- Readiness, migration, and transfer failures are distinguishable from a valid empty memory; transfers, Clear, and migration never overlap.
- Typing stays responsive during transfers; temporary files are always cleaned up.
- Instrumented tests, cross-platform round trips, and installed-IME manual checks are reported separately.

## Implementation (2026-11-08)

Implemented the shared helper and explicit readiness API, migration cleanup on failure, version-1 exporter/importer, process-lifetime transfer controller, launcher navigation and SAF pickers, keyboard-settings links and Clear guards, and localized feedback in all 20 affected resource sets.

Implementation details:

- A transfer reservation covers the picker, database work, and provider I/O, so Clear cannot run in the middle of publication or file capture. Transfers survive Activity recreation and hiding the keyboard within the process lifetime.
- Provider input is capped at 256 MiB, including streams without a reported length. Source validation remains authoritative after capture.
- Learning uses atomic SQL increments with saturation at `Long.MAX_VALUE`, and conflict-safe insertion, to support imported 64-bit frequencies and concurrent imports. Learning retains the larger timestamp when racing with import.
- Clear performs database deletion on `Dispatchers.IO`, then runs emoji cleanup in the caller's Main context while retaining the operation lock. Once deletion starts, cancellation does not interrupt the associated cleanup. Regression tests verify no main-thread disk access under StrictMode, Main-thread cleanup, and transfer exclusion through cancellation.
- Provider open/read failures and private-copy write failures report the generic import-failed message. Format validation and the explicit size limit retain unsupported-file feedback. Regression tests simulate failed provider opens, disconnection during copying, and malformed files, checking feedback, unchanged memory, and temporary-file cleanup.
- Pure File APIs refuse the live store and its sidecar paths. The importer consumes and deletes its private input copy. Failed export output and all private workspaces are cleaned up.
- No fallback from `VACUUM INTO` was needed on the tested emulator. No storage permission, backup-policy change, bundled-data regeneration, or format-version change was introduced.
